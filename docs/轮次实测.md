# 轮次实测：工具改造对 Agent 调用次数的影响

> 结论先行：**大部分成本来自每轮重发的上下文（含约 6.5k token 的常驻工具 schema）。**
> 一次工具输出只有几百 token，上下文是几万 token，所以**先减轮次，再减输出**。
>
> 这里只对比上下文体积（字符/token 估算），不等于账单：实际费用还要看输入 cache 命中率、
> 输出单价（通常高于输入）与供应商计价规则。单次输出也会进入后续轮上下文，
> 并非发完即弃——所以也不是“输出完全不花钱”。

本文记录的是"减少轮次"系列改造的实测数据，不是估算。

## 方法与局限

本文记录的是“减少轮次”系列改造的**小规模**实测，不是估算，也不是普遍结论：

- 每项对照两侧各 1 次运行（n=1），模型行为有方差；只有同模型同任务的两项可比性最好。
- 记录的是调用次数、失败次数与输出字符；**没拿到宿主 usage**，所以不报 token 与金额。
- 上下文通常有 prefix cache：重复前缀大部分命中缓存时单价更低，但不能假定“一定命中”。
  供应商与版本策略都会变，需要按真实 usage 验证。

## 方法

用**真实 Agent**（不是脚本回放）在同一套 fixture 上完成同一任务，逐次记录工具调用。
关键设计：两侧 fixture 内容逐字节相同，任务书相同，唯一变量是**工具是否可用/是否易用**。

fixture（14 个文件）：12 个 `src/svcNN.ts`（各含一个 `export function handle_svcNN`）
+ `src/log.ts`（含一处 `console.log`）+ `README.md`。

任务：① 仓库有多少文件、总大小？② 哪些文件含 `handle_` 导出？③ 把 `log.ts` 的
`console.log` 改成 `console.error` 并确认生效。

## 实测结果

### 1. `fs_inspect` 有无对照（v0.9.0，同模型同任务）

| | 有 `fs_inspect` | 无 `fs_inspect` |
|---|---|---|
| 调用次数 | **4** | **5** |
| 失败次数 | 0 | 0 |
| 输出字符 | 981 | 859 |

调用序列：

```text
有:  fs_inspect(规模+命中分布+样例)  → fs_edit → fs_grep → fs_write   = 4
无:  fs_glob(规模) → fs_grep(命中)  → fs_edit → fs_grep → fs_write   = 5
```

**结论**：`fs_inspect` 把「`fs_glob` + `fs_grep`」合成一次，**省 1 轮**；但它自身输出
比那两个加起来多 122 字符（多给了样例）。本质是"2 合 1"，不是质变。

### 2. `fs_edit` 顶层简写（v0.8.0 → v0.9.0）

同任务三次独立运行（不同 agent、不同 fixture 路径），**3/3** 都把 `pattern`/`all`
直接放顶层，被 `E_BAD_ARGS` 拒绝后重试——每次白费一轮。

改成接受顶层简写后的复测：

| 版本 | A 侧 | B 侧 |
|---|---|---|
| v0.8.0（修复前） | 5 次，**1 次失败** | 7 次，**1 次失败** |
| v0.9.0（修复后） | 4 次，0 失败 | 5 次，0 失败 |

**结论**：这类"模型自然写法被工具纠正"的坑，每次踩到就多一轮；改成接受后归零。

### 3. 其它改造的收益来源（机制明确，未单独做对照）

| 改造 | 机制 | 省轮 |
|---|---|---|
| `fs_write files` 批量 | 建 N 个文件从 N 次变 1 次 | **N−1** |
| `fs_grep` 首行带分布摘要 | 替代 `output=files` + `output=count` 两轮 | 1–2 |
| `fs_grep expand=block` | 合并「grep 拿行号 → `fs_read block=true`」 | 1 |
| `fs_grep` 默认 limit 100→200 | 少一次 `offset` 翻页 | 1（边界时） |
| `fs_edit` 半行 `old` 警告 | 消掉「改完不自知 → 下轮 fs_read 发现 → 再改」 | 2–3（踩坑时） |

## 诚实的评估

- **除批量写入外，其余每项都是"省 1 轮"级别的改进，不是数量级提升。**
- 对真实文件密集型任务（原 57 次调用）的累计效果约 **57 → 39 轮（−32%）**，
  主要贡献来自 `fs_write files` 批量那一项。
- `fs_inspect` 的固定成本是本机实测的 +276 B 描述/参数体积（P0 基线：9 个工具
  desc+schema 合计 17.4 KB）；这里不直接换算成账单 token，也没有 cache 命中率数据。
- 每次实测每侧只有 1 次运行（n=1），模型行为有方差；上面标注为"对照"的两项
  是同模型同任务，可比性最好。

## 复跑方式

需要一个真实 Agent 环境（本仓库的评测流程用 DSH 的 subagent）：

1. 按上文造两个内容逐字节相同的 fixture 目录；
2. 给两个 agent 相同任务书，一侧禁用 `fs_inspect`（或在旧版本上跑）；
3. 让 agent 把每次调用记进报告，对比调用次数与失败次数。

注意：这类测量的**变量是模型行为**，只能靠"同模型 + 同任务 + 同 fixture"控制，
不能像 `tests/bench.py` 那样在 CI 里机械复跑。

## 延迟实测：Rust 层压到哪一步了

问题：0.5–0.9ms 对一个"读 5 行文件"偏高，纯 Rust 读文件应该只要几十微秒。逐层拆开看。

### 方法：用 `ping` 与 `detail=server` 做地板

```text
ping                  → 只走管道与 JSON 编解码，不碰任何工具（IPC 地板）
fs_stat detail=server → 再加工具分发 + 参数校验，不碰文件（分发地板）
fs_stat detail=meta   → 再加路径解析 + 一次元数据系统调用（IO 地板）
fs_read / fs_write    → 完整工具
```

实测方式：起一条长驻 `fsops mcp`，每种调用预热 30–50 次后取 400–600 次的中位数。

### 优化前（v0.9.0 之前）

| 调用 | 中位 |
|---|---:|
| `ping`（IPC 地板） | 30µs |
| `fs_stat detail=server` | 226µs |
| `fs_stat meta` | 287µs |
| `fs_read` 5 行 | 384µs |

**发现**：分发+校验花了 226µs，而 IPC 只有 30µs——工具还没碰文件就已经是地板的 7 倍。

根因：`call()` 每次都调 `validate_args()`，而它调 `tool_defs()` **重新构建全部 9 个工具的
schema**（约 10KB JSON、上百字段）。schema 是编译期常量，却被每次调用重建。

### 优化后（`tool_defs()` 用 `OnceLock` 缓存）

| 调用 | 优化前 | 优化后 | 提升 |
|---|---:|---:|---:|
| `ping`（IPC 地板） | 30µs | 44µs | 噪声 |
| `fs_stat detail=server` | 226µs | **41µs** | **5.5×** |
| `fs_stat meta` | 287µs | **93µs** | **3.1×** |
| `fs_read` 5 行 | 384µs | **191µs** | **2.0×** |

**分发+校验已降到与 IPC 地板持平**，这一层到极限了。

插件侧（Node 观测的端到端，release 构建）：

| 场景 | 独立进程 | 长驻会话 |
|---|---:|---:|
| `fs_read` | 34.3ms | **0.31ms** |
| `fs_stat` | 33.3ms | **0.12ms** |
| `fs_grep` | — | 1.6ms |
| 4 路并发一轮 | — | 0.23ms |

### 剩下两处不是瓶颈，没动

**`fs_write` 约 3.5ms，其中 3.3ms 是 `sync_all()` 落盘。**

`dry_run`（全程校验但不写盘）只要 182µs，说明成本几乎全在 fsync。这是「临时文件 → fsync →
原子改名」防"写一半崩溃留半截文件"的必要代价。端到端算账：40 轮任务写 5 次共 17.5ms，
而 40 轮 LLM 往返是 40–120 秒——**占比 0.02%–0.04%**。为看不见的延迟牺牲崩溃安全不划算。

**`fs_read` 的 191µs 主要花在读整个文件做编码检测与 hash。**

要检测 GBK/UTF-16/BOM 并给出一致的内容指纹，就必须读全文。改成按行流式读能省时间，
但会牺牲编码识别准确性和 hash 一致性——那是功能换性能，不是纯优化。

### 结论

**Rust 层已从「有明显浪费」压到「接近 IPC 地板」。** 继续往下压的边际收益很小：
剩下的 44µs 是管道 + JSON 编解码，除非改协议（如共享内存），而那会牺牲跨语言兼容性。

真正的下一层空间不在 Rust，而在**减少调用次数**——见上文。
