# P1b 真实 Agent 对照（探索规模 6 × 3 × 2）

> 日期：2026-11-18。对应计划 `docs/Agent易用性优化计划.md` 的 P1b 与基线 `docs/Agent易用性评测基线.md` 9.2。
> **规模是探索级（每任务每侧 3 次），不是正式验收规模（16 × 5）。** 本文只报实测，不做显著性声明。

## 1. 结论

同一个模型、同一套 fixture 和任务书，唯一变量是工具集：

| 指标 | fsops 侧 | 原生工具侧 |
|---|---:|---:|
| 运行 / 成功 | 18 / **18** | 18 / **18** |
| 工具调用总数 | **67** | 103（+54%） |
| 依赖批次（各任务中位之和） | **23** | 26 |
| 失败调用 | 0 | 0 |
| 原始输入 token | 430,488 | 112,921 |
| 缓存命中 token | 405,116（94.1%） | 90,752（80.4%） |
| **未缓存输入 token** | 25,372 | **22,169**（−12.6%） |
| 输出 token | **11,135** | 12,332 |
| 墙钟（六任务中位） | 8.1 s | 8.2 s |
| 常驻 schema | 13,863 B | 2,083 B |

可以确定的三点：

1. **正确性没有差异**：两侧都 18/18 通过独立校验（磁盘内容 + 答案），没有一次未授权文件修改、编码破坏或误报成功。
2. **fsops 用少 35% 的调用完成同样的任务**（67 vs 103），差异集中在批量能力：`fs_read reads` 一次读 6 个文件的指定区间（R03：5 vs 19 次调用），`fs_edit files` 一次提交 3 个文件（R06：9 vs 23）。
3. **fsops 的 schema 成本基本被 prefix cache 吸收**：原始输入是原生侧的 3.8 倍，但缓存命中 94%，**未缓存输入只多 3,203 token**（36 次运行合计，约每次 89 token）；输出反而少 10%。

不能从本次数据得出的结论（见第 5 节）：参数误用率下降、恢复调用减少、跨模型通用性、账单节省比例。

## 2. 方法

- 模型：`auto/deepseek-v4.1-flash`（本地 OpenAI 兼容网关 `127.0.0.1:3425`，返回 `prompt/completion/cached` 精确 usage）。
- 宿主：评测 harness `tests/agent_bench.py` 直连 API，两侧工具集由脚本注入；不使用仓库 AGENTS.md 的 fsops 路由要求，两侧任务书逐字相同。
- fsops 侧：9 个 `fs_*` 工具，schema 直接取自 `fsops schema`（真源），调用走持久 MCP 会话（复用 `tests/task_bench.py` 的 `Mcp`）。
- 原生侧：宿主等价工具六件套——`read_file`（带行号、分页）、`write_file`、`edit_file`（唯一匹配校验）、`grep`、`find_files`、`run_command`（bash）。
- 隔离：每次运行 `mkdtemp` 独立目录，跑完删除；两侧 fixture 逐字节相同；运行前对全部文件做 sha256 快照，用于「未授权文件未变」断言。
- 校验：独立校验器读磁盘与答案，不采信模型自述（如 R05 断言 `counter.ts` 精确等于期望内容，而不只看模型说"改了"）。

复跑：

```powershell
python tests/agent_bench.py --smoke            # 1 任务 × 1 次 × 2 侧，先验 harness
python tests/agent_bench.py                    # 6 任务 × 3 次 × 2 侧（本文数据）
```

原始记录落在 `tests/agent_bench_out/runs.jsonl`（已 gitignore，含完整调用链与 usage）。

## 3. 评测本身修掉的两个坑（影响过第一版数据）

第一版冒烟跑出「fsops 18 轮 / 32 次调用 / 261k 输入」，取证后发现不是产品差异，是 harness 缺陷：

1. **MCP 进程 cwd 没设到运行目录**。`fs_exec` 的缺省工作目录是服务进程 cwd，模型执行 `git ls-files` / `python` 数文件时读的是 fsops 仓库本身（一次输出 32,810 字符），随后模型一直在错误前提上打转。已给 `Mcp` 增加 `cwd` 参数，评测时设为运行目录。
2. **MSYS 风格路径被重复拼接**。Windows 的 `Path.is_absolute()` 不认 `/c/...`，harness 把它当相对路径拼到临时目录下，产生 `E_NOT_FOUND /c/c/Users/...`。已改为：`/c/...`、`~/...`、`C:/...`、UNC 一律视为绝对；原生侧再把 `/c/` 映射为 `C:/`。

修正后同一任务（R01）两侧都是 5 轮 / 7 次调用 / 0 失败，验证了「唯一变量是工具集」。**这条经验对后续真实评测同样适用：先确认所有工具的工作目录一致，再看数字。**

## 4. 逐任务明细（中位数）

| 任务 | 类型 | fsops 调用 | native 调用 | fsops 批次 | native 批次 | fsops 未缓存 tok | native 未缓存 tok | 双方结果 |
|---|---|---:|---:|---:|---:|---:|---:|---|
| R01 定位（14 文件） | 只读 | 21 | 23 | 6.0 | 6.0 | 2,715 | 2,336 | 18/18 成功 |
| R03 六文件指定区间读 | 只读 | **5** | 19 | 2.0 | 2.0 | 1,222 | 1,332 | 全对 |
| R05 函数内两处同名语句改一处 | 写 | 9 | 9 | 4.0 | 4.0 | 986 | 598 | 全对 |
| R06 三文件批量改名 | 写 | **9** | 23 | 3.0 | 4.0 | 1,234 | 1,164 | 全对 |
| R07 三处相同字符串改指定上下文 | 写 | 8 | 10 | 4.0 | 4.0 | 1,102 | 810 | 全对 |
| R08 任务书与磁盘写法不符 | 写 | 15 | 19 | 4.0 | 6.0 | 1,228 | 1,136 | 全对 |

工具使用分布：

- fsops：`fs_read` 23、`fs_grep` 12、`fs_edit` 12、`fs_exec` 7、`fs_glob` 6、`fs_stat` 4、`fs_inspect` 3
- native：`read_file` 42、`edit_file` 21、`run_command` 19、`grep` 18、`find_files` 3

fsops 侧没有出现参数校验失败（0/67），0.11.3 修的三类误用（`fs_edit` 顶层 old/new、`fs_file` 的 `operation`、`fs_grep` 的 `output_mode`）在本样本未复现。native 侧同样 0 失败——它只有 6 个参数面很小的工具，这轮任务也没压到它的错误分支。

`fs_read` 在 fsops 侧承担了 34% 的调用；`read_file` 在 native 侧承担 41%。批量参数（`reads`、`files`）是调用数差异的主要来源。

## 5. 局限与未测项（如实列出）

- **n=3，每任务每侧 3 次**：只能排查评测问题和方向性差异，不能声称统计显著。计划要求正式验收用 16 任务 × 5 次。
- **单一模型**：只测了 `deepseek-v4.1-flash`。跨模型（尤其是原生 function-calling 较弱或很强的模型）结论可能不同。
- **宿主是模拟的**：harness 直连 API，工具集由脚本注入；原生侧的六个工具是本仓库实现，不是 Claude Code / Hermes / DSH 的真实工具。真实宿主的并行调度、错误包装、权限提示都会影响结果。
- **没压到恢复路径**：R08 本意是触发「目标文本不匹配 → 用候选内容修正」，但模型都先读盘再改，两侧 0 失败。`E_STALE`/`E_AMBIGUOUS`/`E_LOCKED` 的模型行为仍未被测量，P3 的「模型不因提示放弃保护」依旧缺证据。
- **缓存是网关行为**：94% 命中率来自同一前缀连续调用；换供应商、换 cache 策略、或任务间隔较长时，未缓存输入会显著上升。不能把「原始输入 430k」直接当账单，也不能把「94% 命中」当保证。
- **fixture 是我写的**：6 个任务都偏「有明确目标文本」的常规任务，不覆盖大仓库导航、跨语言、Office/PDF 等场景。

## 6. 后续优化：schema 瘦身与宿主参数别名（2026-11-18）

### 6.1 体积

9 个工具的 schema 从 **18,476 B 降到 15,319 B（−17.1%）**，紧凑 JSON 口径，参数集合未变：

| 工具 | 改前 | 改后 | 变化 |
|---|---:|---:|---:|
| fs_read | 3,958 | 3,013 | −24% |
| fs_edit | 3,009 | 2,503 | −17% |
| fs_grep | 2,994 | 2,332 | −22% |
| fs_exec | 2,190 | 1,714 | −22% |
| fs_glob | 1,785 | 1,512 | −15% |
| fs_write | 1,237 | 1,084 | −12% |
| fs_inspect | 1,214 | 1,124 | −7% |
| fs_file | 1,370 | 1,318 | −4% |
| fs_stat | 719 | 719 | 0 |

做法只有三种：删除 `reads`/`edits` 嵌套项里与顶层重复的描述、删掉与工具描述「模式表」重复的互斥枚举、压缩实现细节（如 `limit` 的三种计数口径）。**没有删参数、没有换英文**——实测中英文 token 完全相等（同一段 183 token），省 token 只能靠删信息。

### 6.2 别名归一

`fs_grep` 新增 `output_mode` → `output` 的键映射，以及宿主枚举值映射（`content`→`matches`、`files_with_matches`/`file_paths`→`files`）。别名不写进 schema，模型看不到就不会依赖；正式参数优先，不会覆盖显式给对的键。

只映射键名不够：P1b 首轮里模型传 `output_mode: "content"`，键归一后仍被 `enum` 拒绝（宿主的 `content` ≠ fsops 的 `matches`）。值映射补上后，R06/R08 各 3 次复跑 **0 失败调用**。

### 6.3 对任务表现的影响

同规模 6 任务 × 3 次 × 2 侧复跑（n=18，模型与 fixture 不变）：

| 指标 | 改前 | 改后 |
|---|---:|---:|
| fsops 成功 | 18/18 | **18/18** |
| fsops 调用 | 67 | 75 |
| native 调用 | 103 | 95 |
| fsops 未缓存输入 tok | 25,372 | 27,883 |
| fsops 输出 tok | 11,135 | 10,976 |

调用数与未缓存 token 都在单次运行波动范围内（R01 一次 8 轮探索把中位数拉高），**没有证据表明瘦身改变了任务表现**——既没有变好也没有变坏。这符合预期：schema 只占单轮输入的一小部分，P1b 里两侧未缓存增量本来就只差 3k token。

结论：schema 瘦身是**成本优化**，不是效果优化；要减少调用轮次，还得靠批量参数（`reads`/`files`）和别名归一这类「不让模型失败一次」的改动。
